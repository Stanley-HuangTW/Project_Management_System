這份文件記錄目前排定要做、但還沒開始或還沒做完的功能,依使用者指定的優先順序排列。
**每完成一項,先回報使用者、等確認後再開始下一項**,不要連續做完全部才一次回報。

## 1. 項目卡片新增「連結」分頁(已完成,commit `5e6f8e1`)

**需求**(使用者原話):「新增一個 SHEET,功能是上傳 URL 資訊,讓使用者可以將雲端連結或
網址放置此資訊」。

對應畫面:`ItemDetailModal`(`src/components/board/ItemDetailModal.tsx`)目前的分頁是
更新 / 檔案 / 活動紀錄 / 項目卡片 / 待辦事項 / 工時與費用。新增一個「連結」分頁,放在
「檔案」分頁旁邊——跟附件是同一類「這個項目的外部資料」,但檔案是上傳進系統的檔案本體,
連結是外部網址(雲端硬碟、Google Sheet、外部文件、Figma 等),不應該混在同一個清單裡。

### 設計方向

- **資料模型**:新增 `ItemLink` model(對應現有 `Attachment` 的結構,但存 `url` 不存
  檔案路徑):`id`、`itemId`、`url`、`label`(使用者自己取的顯示名稱,選填,沒填就顯示
  網址本身)、`createdById`、`createdAt`。手寫 migration,不跑 `prisma migrate dev`。
- **Server actions**(`src/lib/actions/itemLink.ts`,仿照 `attachment.ts` 的寫法):
  `listItemLinks`、`addItemLink(itemId, url, label)`、`deleteItemLink(linkId)`。
  `addItemLink` 要驗證 `url` 是合法網址格式(避免存進奇怪的字串),比照
  `requireItemBoardAccess` 做權限檢查。
- **UI**:新增 `src/components/board/item-detail/LinksTab.tsx`,仿照
  `src/components/board/item-detail/` 底下既有分頁(檔案分頁的 `AttachmentsTab.tsx`
  或類似檔名——動手前先確認實際檔名)的版面:一個輸入網址 + 選填標籤的表單、「新增」
  按鈕,下面列出已加的連結(可點擊開新分頁、可刪除)。
- 在 `ItemDetailModal.tsx` 的分頁清單裡插入「連結」,掛上這個新分頁。

### 驗證方式

- `npx tsc --noEmit`、`npm run lint`、`npx vitest run`。
- Docker 重新 build + up,套用新 migration。
- 瀏覽器:開一個項目卡片,到「連結」分頁新增一個網址(例如一個 Google Sheet 連結)
  跟一個自訂標籤,確認存檔後清單顯示正確、點擊會開新分頁、可以刪除。

## 2. 資料庫備份管理功能(系統設定)(已完成,commit `39f229c`)

**需求**(使用者原話):「系統設定可以設定資料庫備份頻率與時間,然後也可以看到資料庫
各備份的檔案,可以選取那一個資料庫備份資料回覆,也可以設定幾天前的備份資料可以清除」。

**風險**:「回復」會覆蓋現有資料庫內容,是這批待辦事項裡風險最高的一個,設計跟實作都要
格外小心,做完要請使用者在正式環境外先驗證一次。

### 現有基礎(已經存在,不用重做)

- `scripts/backup-db.sh`:對資料庫跑 `pg_dump` 壓成 `backups/hrapp_db_<時間戳記>.sql.gz`,
  把附件 volume 打包成 `backups/uploads_<時間戳記>.tgz`,並自動清除超過保留天數
  (預設 60 天,可用 `RETENTION_DAYS` 環境變數調整)的舊備份。寫入時用 `.part` 再改名,
  指令失敗不會留下看起來像備份的空檔。
- `docs/deploy-linux.md` 第 5 節:目前是透過 `crontab` 手動排程(`0 3 * * 1 ...`
  每週一凌晨 3 點),還原要手動跑 `gunzip -c ... | psql ...`。
- 這些都是**命令列**層級的腳本,系統設定裡完全沒有對應的畫面。

### 要設計的部分(動手前要跟使用者確認的點)

1. **排程怎麼觸發**:這個專案已經有一套「伺服器自己算完、自己觸發」的排程心跳機制
   (`server.js` 的 primary process 定時打 `/api/internal/weekly-report-tick`,見
   `docs/weekly-report.md`/`INTERNAL_CRON_SECRET`)。備份排程可以比照這個模式加一支
   `/api/internal/backup-tick`,取代現有的 `crontab` 寫法——但這樣兩套排程(週報、備份)
   都要在 `server.js` 的同一個 `setInterval` 迴圈心跳,還是分開各自一個,需要先確認。
2. **備份檔案清單怎麼「看得到」**:`scripts/backup-db.sh` 寫在 server 本機的
   `backups/` 目錄——Next.js app 的 container 需要能讀到這個目錄(volume mount),系統
   設定頁面才能列出檔案清單、顯示大小與時間。目前 `docker-compose.yml` 有沒有把
   `backups/` 掛進 app container,需要先確認。
3. **「回復」的執行方式**:`psql` 還原是一個命令列操作,Next.js app 本身不適合直接在
   request handler 裡執行(還原要停讀寫、時間可能很長);初步構想是 app 寫一個「待還原」
   的標記/佇列,由 server.js 的心跳或一支獨立 script 實際執行 `pg_dump`/還原指令,執行
   完再回報結果——但也可能有更簡單的做法,要先跟使用者確認「回復」操作可以接受多大的
   停機時間、要不要有二次確認機制(例如要求輸入看板名稱或當前日期才能觸發)。
4. **權限**:這個功能只能給 ADMIN,而且「回復」這個動作建議要有比一般 ADMIN 操作更高的
   確認門檻(例如要求再輸入一次密碼,或是输入一段確認文字)。

### 下一步

這一項**先進入設計討論**,不要跳過確認直接動手——上面 1~4 點都需要使用者先選方向。

## 3. 工時統計系統(含非專案工時)

**需求**(使用者原話):「目前工作項目是根據專案 ASSIGN 任務給人員進行工時的更新,但是
執行者有時有例行會議或突發事件 ISSUE 解決,不在開發任務上面,但是我希望可以統計此人員
每週、每月、每天、限定固定區間,進行的工作事項時間統計,因此還需要有一個工時管理系統」。

### 現況(已經存在,不用重做)

- 工作項卡片的「工時與費用」分頁已經有「實際工時」登記(依日期、每筆可加備註,
  見 `src/lib/actions/...` 工時相關 action),但這些工時一定要掛在某個看板的工作項上。
- 儀表板已經有「工作量總覽」「工作量明細」「過度配置」,但這些統計的是**配置比例**
  (指派了多少 %),不是**實際登記的工時小時數**,而且同樣只涵蓋掛在工作項上的配置。

### 要討論的缺口

使用者要統計的是「這個人這週/這個月/自訂區間總共花了多少工時」,但來源不是只有工作項:
- 開發任務的工時(已有)。
- 例行會議(週會、站會……)。
- 突發 ISSUE 處理(不一定對應到看板上的某個工作項,也可能事後才知道要花多少時間)。

這代表現有「工時一定要掛在一個 Item 底下」的資料模型可能不夠用,需要先確認方向,例如:

1. **方案 A**:比照 Jira/Harvest 的做法,拉出一個獨立的「工時紀錄」model,`itemId` 改成
   選填——可以選擇性掛在某個工作項上,也可以只填「類別」(會議/ISSUE/其他)+ 自由文字
   說明,不綁任何工作項。儀表板/報表另外做一個「工時統計」頁面,依人員、依類別、依週/月/
   自訂區間彙總。
2. **方案 B**:在現有工時登記表單上加一個「類別」下拉(開發任務/會議/ISSUE/其他),
   當選「開發任務」才要求選工作項,其餘類別可以不綁工作項、改填自由文字當「做了什麼」。
   比方案 A 改動小,但如果以後要對應「這個 ISSUE 花多少錢」之類的追蹤就比較難延伸。
3. 不管哪個方案,都要決定:這些非專案工時要不要也送審(比照現有工時審核流程)、要不要
   算進任何成本報表(目前 AC/EVM 只算工作項上的工時)。

### 下一步

這一項排在最後,而且使用者已經明確說「做法需要請你幫我想」——**先回去跟使用者討論
方案 A/B(或其他做法)**,確認資料模型方向後才開始寫 schema/UI,不要先動手。
